# Flickr Turnstile: сравнение данных VM до упаковки

## Граница измерения

В двух **живых** загрузках Flickr перехвачен объект аргумента функции VM
непосредственно после `XMLHttpRequest.send` для первого и второго `/fo`.
Frozen Chrome 152 получил токен; Mimic отправил оба POST, получил `600010`,
поле токена осталось пустым. В этих запусках не подменялись пиксели, ответы
сервера, объекты VM или сетевые данные. Это не offline replay. Диагностический
код лишь читает значения аргументов и не меняет production Mimic.

Успешный Chrome захват скопирован в игнорируемый
`.build/flickr-audit/chrome152-success-frozen-20260926/`; размеры и SHA256
добавлены в его `receipt.json`. Сырые объекты, HTML и чанки содержат данные
сеанса и остаются вне Git. Полный локальный реестр листовых различий с типами,
длинами и HMAC находится в
`.build/flickr-audit/vm-analysis/prepack-aligned-diff-registry.json`. Его
строит `.build/align_flickr_prepack.cjs`. Ключи вложенных объектов сами могут
содержать данные сеанса, поэтому и реестр остаётся приватным. Ключ HMAC
хранится только локально.

## Сопоставление

Первый объект перед POST содержит по 50 собственных ключей в обоих браузерах,
в JSON проецируются по 45. Получилось 27 различных и 40 одинаковых листовых
значений. Разницы в наборе полей верхнего уровня нет; в `VbYF3` у Mimic на
один элемент больше (3 против 2). Остальные отличия первого объекта могут
включать времена, идентификаторы сеанса и значения профиля; сами по себе они
не доказывают дефект браузерного API.

Второй объект перед POST содержит 101 собственный ключ в Chrome и 100 в
Mimic; через JSON видны соответственно 90 и 89. Из них 51 именованное поле
есть в обоих. Остальные — числовые блоки: 39 в Chrome, 38 в Mimic. Их порядок
различается, поэтому сравнение по числовому индексу ошибочно. Блоки
сопоставлены по набору полей сверх общего конверта; 34 пары имеют уникальную
точную сигнатуру, три повторяющиеся пустые сигнатуры сопоставлены по порядку,
одна пара имеет частичное совпадение. Один блок Chrome не имеет пары.

После выравнивания: 768 различных и 2359 одинаковых листовых значений во
втором объекте. Из 768 различий 62 содержат отсутствующее значение с одной
стороны, 8 меняют тип, 311 имеют тот же тип, но другую длину, 387 имеют те же
тип и длину, но другое значение. Это **наблюдаемые различия двух независимых
живых сеансов**, а не 768 подтверждённых ошибок Mimic. Массивы внутри блоков
сравниваются по позиции; смена порядка элементов может завышать счётчик.

из потенциально значимых для сервера различий.

## Установленная причина отказа Trusted Types

Отдельный диагностический прогон Mimic записал стеки создания указанного
`EvalError` (`.build/flickr-audit/vm-analysis/mimic-tt-stacks.json`). Он также
отправил два POST и получил пустое поле токена. Шесть стеков образуют три пары:
`navigator.gpu`, `OffscreenCanvas.getContext` и конструктор
`OfflineAudioContext`. Все сходятся в `ensureLazyDomain` в
`internal/webapi/surface.js`. Там реализация подсистемы догружается через
`eval(host.lazyDomainSource(name))`. CSP iframe содержит
`require-trusted-types-for 'script'`; его политика `default.createScript`
возвращает пустую строку для произвольного кода. `evalSourceResolver` корректно
отвергает такую замену, но это означает, что **внутренний код Mimic ошибочно
проходит через проверку, предназначенную для авторского `eval`**. После первого
отказа lazy domain помечается как `failed` и повторно выбрасывает ту же ошибку.
Таким образом, минимум три группы Web API в этой загрузке становятся
недоступными до того, как VM формирует второй объект. Это архитектурная причина,
а не особенность Flickr; потенциально затрагивает любой документ с таким CSP.

Стеки связывают ошибку Trusted Types с реализацией lazy domains. Они не
доказывают, что все остальные перечисленные поля расходятся исключительно
по этой причине. Для окончательной атрибуции каждого поля нужно сопоставить
его с операцией VM, сохраняя отдельный учёт данных сеанса и времени.

## Вывод и пределы

Mimic действительно достигает второго POST, но входные данные VM до его
упаковки уже отличаются от успешного Chrome по структуре. Установлен общий
дефект загрузки lazy domains при CSP: внутренний `eval` блокируется Trusted
Types, и VM получает ошибки вместо результатов части проб. Ещё один блок
целиком отсутствует. Нельзя пока утверждать, какое именно поле проверяет
сервер и является ли ошибка Trusted
Types единственной причиной `600010`. Для причинного вывода требуется связать
поля с вызываемыми функциями VM и повторить сравнение с учётом меняющихся
данных сеанса. Нового прогона Chrome для сохранения уже имеющейся успешной
трассы не требуется.
